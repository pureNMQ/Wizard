# 领域文档

## 何时查阅与记录

讨论游戏概念、修改数据模型或命名公共业务接口时，先查现有规格与根目录 `GLOSSARY.md`（若已存在）。涉及对象所有权、状态归属、持久化边界等重要取舍时，查相关 `docs/adr/` 记录（若已存在）。

当前未建立术语表与 ADR 目录。文件缺失不会阻止正常开发；有实际术语需要统一或真实决策需要留痕时再创建，按任务范围补齐即可。

## 内容边界

- **规格**描述玩家可见规则和验收要求；同一规则只在规格保留正文，其他文件引用对应编号。
- **术语表**解释游戏概念及区别，如“物品定义”“物品实例”“背包格”“装备槽”；避免把 C++ 类名或候选架构写成领域定义。
- **技术提案**列出尚未验证的实现选项，集中在 [implementation-proposals.md](../planning/implementation-proposals.md)。
- **ADR**记录难以逆转、缺少背景会令人困惑、且存在实际取舍的决定。普通命名或可调数值在票据中记录即可。

ADR 使用 `docs/adr/<NNNN>-<slug>.md`，包含状态、上下文、备选方案、决定、后果与验证/任务链接。以真实证据将 proposed 更新为 accepted；后续替代时保留原记录并链接新决定。

## 冲突处理

指出冲突的文件、适用范围和实际影响；玩法以已确认规格及用户后续指令为准，工程取舍结合 UE5.4 本机契约和验证结果处理。更新权威正文，并将其他位置改为引用，避免两份相互矛盾的规则。
