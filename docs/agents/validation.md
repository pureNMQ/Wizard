# 验证流程

## 按改动选择证据

先读取对应票据的验收与失败路径，再选择下表检查。记录准确范围；“未执行”和“不适用”分别写明原因。

| 改动 | 必需检查 | 适用边界 |
| --- | --- | --- |
| 开发约定与任务文档 | 本地链接、规格编号、任务依赖/状态、权威来源一致性；Git diff 检查 | 不因纯文档改动声称完成构建或游戏验收 |
| C++、反射声明或模块依赖 | 实际 UHT/UBT 构建；受影响规则和生命周期的测试 | UBT up to date 与干净重编译分别记录，Live Coding 结果不能代替结构变更的完整构建 |
| 业务规则、事务与存档 | 公开接口的成功/失败用例、跨组件状态一致性；受影响的运行验证 | 金币/数量守恒、失败不提交、保存顺序与往返恢复需直接断言 |
| GAS、输入或 UI | 构建/相关自动化，加 PIE 与实际按下/持续/松开/取消、焦点/暂停/重建检查 | 反射调用证明能力或移动接口可用，不能代替物理输入和 UI 路由验收 |
| 地图、碰撞、导航、网格或表现 | 加载/保存、受影响区域的多视角检查、PIE 通行/碰撞、目标地图 Cook | 保存变换不等于视觉正确；导航路径存在不等于玩家实际通过 |
| 软引用、图标、资源扫描或 Cook 规则 | 目标平台 Cook；对应资源在独立游戏包中实际加载 | 编辑器能加载与独立包可用分别验收 |
| 卡顿或性能回归 | 固定对象、操作和测量条件的前后对照，记录帧耗时/长停顿及相关日志 | 排除后台/交互限速、着色器编译等混杂因素；一次流畅样本不能证明底层根因 |
| 发布交付 | Windows 成品包、退出重启读档、完整循环和计划中的全量回归 | Cook 成功不等于完成 Build/Stage/Package 或成品运行 |

模型编辑期间保留用户的场景改动。销毁对象或批量资产操作优先用专用接口，超时后先核对实际落盘状态再决定重试。已有反射桥接序列化异常见 [素材清理记录](../planning/asset-cleanup-result-2026-10-27.md)。

## 记录格式

票据中每项证据写明：日期、检查对象/版本、命令或步骤、预期、实际结果、退出码（适用时）、日志或截图位置、未覆盖范围。短摘要保存在票据中；原始构建/测试/Cook 输出放 Git 忽略的 `Saved/<TaskId>/` 或专项检查目录。

成功的工程自动化测试源码和复现工具纳入版本控制。若原始证据位于本地忽略目录，交付时保留足够的命令与摘要以便复跑，不把只在本机存在的截图当作唯一验收描述。

提交前检查未保存的 UE 资源、实际 Git 暂存清单与 LFS 指针，保留用户已有内容；学习资料与本机生成目录保持忽略。提交/推送结果与功能验收结果分别记录。

## 执行入口

构建、自动化与最小 Windows 包统一使用 [构建与测试说明](../BUILD_AND_TEST.md) 中的 `Tools/Build/Invoke-Wizard.ps1`，原始结果写入 `Saved/T01/`。具体通过范围与已知限制以 [T01](../../.scratch/wizard-demo/issues/01-environment-and-quality.md) 的实际记录为准。

执行前保存资源并检查编辑器/Live Coding 状态；冷编译、增量编译、迭代 Cook 与干净 Cook 分别记录。游戏目标和编辑器目标分别构建。新增业务测试后，扩展真实测试覆盖，不把环境检查数量当作玩法覆盖率。

## 双轴审查

- **Standards**：按 [编码与框架规范](../CODING_STANDARDS.md) 的相关条目检查，说明依据是引擎契约、框架实践还是项目约定。
- **Spec**：按规格 R 编号及票据检查玩家可见行为、基础范围、数据驱动演示和失败路径。

两项均记录问题或通过依据；代码风格通过不代表玩法符合规格，运行成功也不能替代生命周期和状态一致性检查。审查方式按任务规模选择，不因本约定自动创建额外聊天或委派任务。
