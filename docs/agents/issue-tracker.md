# 本地任务追踪

生效日期：2026-10-28。任务使用仓库内 Markdown，位置为 `.scratch/<feature>/`。

## 文件与权威来源

- `spec.md` 保存已确认规则与验收编号。
- `plan.md` 保存排期、任务导航和整合目标；日期是计划，完成状态以票据为准。
- `issues/<NN>-<slug>.md` 是正式票据，编号从 01 开始；Status、依赖、验收与验证记录以票据为准。
- `issues/_template.md` 是新增任务模板；已有任务的拆分、合并需同步计划入口与相关依赖。
- 当前项目入口为 [Wizard 计划](../../.scratch/wizard-demo/plan.md)。

“创建票据”或“发布到任务追踪”表示写入上述本地文件。GitHub 远程用于版本管理；创建 GitHub Issue、给他人发送消息分别按用户授权执行。

## 状态与依赖

| Status | 含义 | 进入下一状态的条件 |
| --- | --- | --- |
| draft | 范围或验收尚待细化 | 明确目标、规格、失败路径与验收后转 ready |
| ready | 票据可执行，尚未开始；可能仍在等待依赖 | Blocked by 列出的前置任务全部 done 后转 in-progress |
| in-progress | 正在执行或验证 | 满足完成条件转 done；实际阻碍导致无法继续时转 blocked |
| blocked | 已开始，但存在不能绕过的具体阻碍 | 记录原因与解除条件；解除后回到 in-progress |
| done | 验收、验证和双轴检查均有证据 | 新发现缺陷时记录复现和影响，按范围重开或新增票据 |

Blocked by 使用本地票据链接，没有依赖写“无”。`ready` 表示排入待办，并不表示依赖已满足；执行者在开始前检查依赖。阻碍不能仅写“等待处理”，应写缺少什么、由谁或哪个任务解除。

任务当前状态只维护在各自票据中，本约定不保留第二份状态快照。

## 单次任务流程

1. **界定**：读取规格、票据和前置交付，写清本次可观察行为、输入/输出与不变量；记录会影响实现的未决问题。
2. **实现**：将票据转 in-progress。按规范实现小步可运行结果；关键业务建立能复现实际失败模式的验证后再修复或扩展。
3. **验证**：按 [验证流程](validation.md) 选择受影响的检查，记录命令或操作、预期、实际结果、日期和证据位置。
4. **审查**：分别填写 Standards（规范）与 Spec（规格）结果，标出失败项、未验证项及适用边界。
5. **交付**：逐项核对验收，补充对应本地学习材料；满足以下完成条件后转 done。提交与推送属于独立的版本管理动作，不替代功能验收。

## done 的完成条件

- 验收条件全部满足，输入/输出、不变量与列出的关键失败情形均有相应证据。
- 受影响的检查通过；不适用项目写明理由，未执行项目如实记录。对验收必需但未执行的检查保持未完成状态。
- Standards 与 Spec 两条轴线各自有结论；阻塞验收的缺陷已解决。
- 交付说明、必要工程文档、数据配置示例及学习材料位置已更新；用户掌握程度与工程完成分别记录。
- 已说明已知限制。局部验证只能证明对应范围，Cook、PIE、实际输入、独立包与读档往返分别验收。

任务内数值初值、类名和接口划分可按规格内的工程取舍推进。改变已确认规则时先与用户确认，再修改规格、受影响票据和计划。
